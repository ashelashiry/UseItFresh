01 What changed today

The build break first, then photo capture — which had been built but never once exercised. Driving it is what found the rest.

WhatDetail
The build break The save action's body took six parameters; its declared argument list had five, so FlutterFlow generated a five-argument call. The part that made it stubborn: declaring the argument alone does not validate, because FlutterFlow refuses a declared argument that any call site fails to supply — so the declaration and the wiring had to land in one push. My earlier attempt read the six identical complaints as six orphaned values and rewrote all the keys, which was the wrong diagnosis of the right symptom.
Photo capture, proven Driven in a browser with the file chooser intercepted — the same path a phone takes right up to the picker. Uploads to food-images/<household>/<uuid>.jpg, returns a signed URL, survives review, lands on the item as image_url with source_type: photo. The card and the details hero both show the person's own picture instead of the illustrative one.
Review screen showed everything but the photo It said "This is what will be recorded" and omitted the one thing you cannot check anywhere else before saving. Now shown above the first fact.
Review screen printed database codes vegetables rather than "Vegetables" — the function only swapped underscores for spaces. Now uses the same words the picker offered. Same family as the dropdown fault you reported on 9 Sep.
Every storage location wore a fridge icon Those three rows were still the stock ListTile FlutterFlow generates — one hardcoded Icons.kitchen on all three, with the raw location_type printed underneath the name. Rebuilt as v3 rows with the right icon per type. The icons already existed and were used correctly on the inventory chips; nothing was binding them here.
Both dropdowns were blank boxes Neither had hint text, so an untouched dropdown said nothing at all. Now "What kind of food is it?" and "Which date is on the pack?". As a side effect the form fits without scrolling.
Migration 6 settled It is not needed. Creating a household as the signed-in user succeeds against the policy as it stands, and the trigger seeds the member, three locations and the shopping list correctly. That open question from the handover is closed.
