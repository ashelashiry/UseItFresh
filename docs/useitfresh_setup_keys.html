App Store Connect API key

~15 min · free

Lets FlutterFlow upload builds to TestFlight without a Mac.

FlutterFlow's Mobile Deployment screen asks for four things. Three come from one Apple page; the fourth comes from the app record, which has to exist first. In this order:

  1. Register the bundle ID. developer.apple.com → Identifiers → new App ID with com.useitfresh.app. It is already set in the project, so it must match exactly. While you are there, this is also where Sign in with Apple gets enabled if you do Track C later.
  2. Create the app record. App Store Connect → Apps → + → New App, using that bundle ID. This is what produces the numeric App ID FlutterFlow wants — you cannot fill that field before the record exists.
  3. Generate the API key. Users and Access → Integrations → App Store Connect API → generate a Team key with the App Manager role. App Manager is the least privilege that can upload builds. Admin also works.
  4. Download the .p8 straight away. Apple shows it once. Miss it and you revoke and start again.

Then fill FlutterFlow's four fields:

FieldWhere it comes from
Issuer IDTop of the App Store Connect API page. One per team, a long UUID.
Key IDThe row of the key you just generated.
Private KeyUpload the .p8 here. This is the secret — it goes nowhere else.
App IDThe numeric Apple ID of the app record: App Store Connect → your app → App Information → General Information → Apple ID. Not the bundle ID.
Lands in FlutterFlow only. .gitignore already blocks *.p8, so it cannot reach the repo by accident. Send me the Issuer ID and Key ID if useful; never the key itself.
Seen on your screen Build Number is empty. App Version reads 1.0.0 but the build number has no value, and a build without one is rejected on upload. Set it to 1, and raise it by one for every upload after that — App Store Connect refuses a repeated build number even for the same version.
Also on that screen Privacy Manifest Configurations is worth opening before the first upload. Apple requires declared reasons for certain APIs, and this app touches the camera, the photo library and local storage. A missing manifest is a rejection after the upload, not before.

Track C — the sign-in buttons that do nothing

Google and Apple sit on the sign-in card as stand-ins today — they are drawn, not wired. Optional, but Apple requires Sign in with Apple on any app that offers another social login, so these two ship together or not at all.

Google sign-in

~20 min · free
  1. Google Cloud Console → APIs & Services → Credentials.
  2. Configure the OAuth consent screen first, or credential creation is blocked.
  3. Create OAuth client IDs: one iOS (bundle com.useitfresh.app) and one Web. The Web one is what Supabase uses.
  4. In Supabase: Authentication → Providers → Google. Paste the Web client ID and client secret, and enable it.
  5. Copy the callback URL Supabase shows there back into the Google credential's authorised redirect URIs.
  6. Send me the client IDs only. I will wire the buttons.
Lands in Supabase only. The client secret stays there.

Sign in with Apple

~25 min · needs the developer account
  1. Apple Developer → Identifiers. On the com.useitfresh.app App ID, enable the Sign in with Apple capability.
  2. Create a Services ID (a separate identifier, e.g. com.useitfresh.signin) and enable Sign in with Apple on it. This is the one that carries the web redirect.
  3. Under Keys, create a key with Sign in with Apple enabled. It downloads a .p8 — again, once only.
  4. Collect your Team ID (top right of the developer portal) and the new Key ID.
  5. In Supabase: Authentication → Providers → Apple. Enter the Services ID, Team ID, Key ID, and paste the .p8 contents into the secret field.
  6. Put the callback URL Supabase gives you into the Services ID's Return URLs.
  7. Send me the Services ID, Team ID and Key ID. Never the .p8.
Lands in Supabase only.
