Where things stand

The prototype is a polished single-user UI mock — 9 pages, 19 components, 5 flat Firestore-style collections, 13 local helper functions. The spec demands a Supabase foundation (auth, households, RLS, realtime) that the prototype never started. The foundation is now ready on the database side: all 13 tables, 45 RLS policies, 3 storage buckets, and the invite-join RPC are live in the UseItFresh Supabase project, and the database password has been reset.

Prototype has

  • Inventory dashboard, search, category chips
  • Add item (manual), item detail + safety tips
  • Recipe generator UI + step-by-step instructions
  • Shopping list, waste analytics, settings

Prototype lacks

  • Auth, households, sharing — no user model at all
  • All AI capture (photo / barcode / receipt / fridge scan)
  • Opened-date & use-by vs best-before tracking
  • Notifications, assessment engine, entitlements

Decided so far

  • Backend: Supabase (same stack as spot-a-paw)
  • Name: Use It Fresh
  • Rebuild from spec, phase by phase
  • First milestone: Phase 1 — Foundation

Prototype ideas the spec doesn’t have

The reverse comparison — features invented for the prototype that are absent from the spec, each with a recommendation. Adopting all five “adopt” rows changes no architecture; they are columns and content on top of the spec’s model.

#Prototype featureIn spec?Recommendation
1 Environmental impact tracking — kg of food waste avoided, per-recipe impact, running total No — §8.12 insights are money-only ADOPT Genuine differentiator; demos beautifully. Add “waste avoided (kg)” to Insights and per-recipe impact.
2 Critical-step flags in recipes — each step can carry a tip and a “critical” safety marker No — §13.5 recipe JSON has no step-level safety ADOPT Dovetails with the §5 food-safety rules: safety inside the cooking flow, cheap schema addition.
3 Recipe metadata — difficulty, calories, prep time on every recipe Partly — inputs exist, output schema doesn’t require them ADOPT Add to the structured recipe JSON; label calories as estimates per the §8.12 rule.
4 Recipe-linked shopping items — each list item can point at its source recipe Partly — has source: recipe but no link to which ADOPT One column (source_recipe_id); enables recipe context and bulk un-adding.
5 Per-food storage & safety tips library — static “how to store, how long it lasts” per category No — only the interactive assessment (§8.8) ADOPT Zero-AI-cost education; reduces assessment queries and builds trust.
6 Storage-location stat cards — item counts per fridge / freezer / pantry on the dashboard Partly — §8.4 counts are urgency-based only NICE-TO-HAVE Secondary dashboard row; trivial once inventory exists.
7 Freshness score — a 0–100 gauge per item No — spec uses 9 discrete statuses (§10) DROP AS SAFETY SIGNAL Implies precision the app can’t claim. At most a visual sort aid — never labelled as safety.

Everything else in the prototype (search, chips, alert-day settings, metric/imperial, checked-off shopping items) is already in the spec in more rigorous form. The prototype’s data model — string dates, no opened tracking, no households — is strictly worse than the spec’s; nothing to salvage there.
